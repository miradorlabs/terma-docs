Terma's hooks never talk to the network. They append events to a local spool and exit, and the spool is delivered later — in the background after a commit or a session ends, or on demand with `terma spool flush`. A backend outage costs nothing at commit time.

`terma spool` is an advanced command: it works as documented but is not listed in `terma --help`.

## How the spool works

<Steps>
  <Step title="Hooks append events">
    Agent hooks and commit hooks write events to the spool under `~/.config/terma/spool/`. No network call is made, and `prepare-commit-msg` finishes in under 50 ms.
  </Step>
  <Step title="Background delivery">
    After a commit or a session end, a detached background process delivers queued events — one request per project, using that project's key. A failed delivery backs off for that project only; every other project's events are still delivered.
  </Step>
  <Step title="Held, not dropped">
    Events for a project that has no key on this machine yet are held until one exists, rather than dropped. Running `terma install` in that repository creates the key.
  </Step>
</Steps>

The spool is bounded at 16 MB; when it is full, the oldest events are dropped so a long outage cannot fill your disk. Expired, pruned, malformed, and unroutable events are reported, never presented as delivered.

## terma spool status

Shows what is queued.

```bash
terma spool status
```

```text
Queued events:   42 (18 KB)
Project keys:    2
Held:            3 events for project 3f59… — no key here yet (run `terma install` in that repository)
```

Depending on the state of the queue, `status` can also report:

| Line | Meaning |
|---|---|
| `Backing off` | The last delivery failed; the next automatic attempt waits until the time shown |
| `Retrying` | A specific project's last delivery failed and it is waiting out its retry window |
| `Held` | Events for a project with no key on this machine |
| `Unroutable` | Events with no project id; they cannot be delivered and leave the queue at the next flush |

## terma spool flush

Delivers everything queued now, one request per project.

```bash
terma spool flush
```

| Flag | Description |
|---|---|
| `--force` | Ignore the failure backoff and retry now |
| `--min-interval <duration>` | Skip when a flush completed more recently than this |
| `--quiet` | Never print or fail (used by background flushes) |

### Exit codes

| Code | Meaning |
|---|---|
| `0` | Everything queued was delivered, including when nothing was queued |
| `1` | Delivery failed for at least one project; its events stay queued and it backs off, while other projects' events are delivered |
| `2` | Nothing was attempted because an earlier failure's retry window is open (`--force` overrides) |
| `3` | The pass ran but left work: events held for a project key, waiting out a retry window, or given up on for age, disk pressure, or being unreadable |

<Tip>
  If events seem stuck, run `terma doctor`. Its **event spool** and **backend receives events** checks show whether the spool accepts writes and whether events reach Terma, with the command that fixes each problem.
</Tip>
