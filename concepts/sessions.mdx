A session is one conversation with a coding agent — such as Claude Code or Codex — or requests grouped from a router such as OpenRouter. Terma rolls each session up with everything it did: turns, model calls, tool calls, token usage, cost, subagents, and the git activity it produced. Sessions are the unit attribution, usage, and the dashboard are built on.

## How a session is identified

A session is identified by its **session id together with its source system** (`claude-code`, `codex`, `opencode`, and so on). The session id is the agent's own id for the conversation, and it is the same value that appears in the `Agent-Session-Id` trailer on commits the session contributed to.

Because ids are only unique within a source, Terma always keys a session by both.

## How sessions are captured

Two channels feed a session, and Terma joins them on the session id:

- **The agent's own telemetry export** carries model calls with their token counts and cost, tool calls, and — when your team's policy collects them — prompts, responses, and tool content.
- **Terma's hooks** record when a session starts and ends, which files it edits, the subagents it spawns, and your plan's usage windows. Hooks append to a local queue and never wait for the network.

How much of each channel exists depends on the agent. See [Integrations](/integrations/claude-code) for what each one reports.

## What a session contains

| Field | Description |
|---|---|
| Source | The agent or system that produced it, such as `claude-code` or `codex` |
| User or API key | The principal the session is attributed to |
| Started, last active | When the session began and its latest event |
| Turns | Prompts from the person, each with the work that followed |
| Model calls | Each call with its model, provider, tokens, and cost |
| Tool calls | Each tool invocation, with arguments and results if exported |
| Tokens | Input, output, cache read, and cache write |
| Cost | The provider's price for the session's model calls, in USD |
| Models and providers | Every model and provider the session used |
| Subagents | Agents the session spawned, and which part of the work each did |
| Git activity | Branches, commits, pushes, and pull requests the session's tool calls produced, and the repositories it touched |

## Events

Inside a session, Terma keeps an ordered event history you can replay in the dashboard:

| Kind | Meaning |
|---|---|
| `session_start` | The session began |
| `turn_start` | A new turn began |
| `user_message` | A prompt from the person |
| `assistant_message` | A response from the model |
| `model_call` | A model request, with its usage once settled |
| `tool_call`, `tool_result` | A tool invocation and its result |
| `tool_decision` | An approval decision about a tool call |
| `compaction` | The agent summarized earlier context to make room |
| `error` | An error during the session |

Content appears only when your team's policy collects it.

## Session totals versus usage over time

A session's totals cover its whole life. The dashboard's usage charts instead sum spend that settled inside a time window. A session that started yesterday and ran past midnight counts toward today's usage only for the part that happened today, so the two views legitimately differ whenever a session straddles the window's edge.
