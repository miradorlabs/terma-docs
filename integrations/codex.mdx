Terma supports OpenAI's Codex as one choice, **Codex TUI & Desktop**. The `codex` shell command, the desktop app, and the IDE extension share Codex's user-level configuration, hooks, and trust settings in `~/.codex`, so one setup covers all of them.

## Set up

Run `terma setup` once on your machine and choose **Codex TUI & Desktop** when asked:

```bash
terma setup --harness codex
```

Then restart Codex — including the desktop app and any background Codex process — so it loads the new configuration. See [`terma setup`](/cli/setup) for every option.

Setup approves terma's own Codex hooks for you, so there is no separate review step in Codex. If you change terma's hook entries by hand, Codex asks you to trust them again; run `terma setup` to restore them.

Sessions are collected only where your team's collection policy allows: in a repository the policy lists, or everywhere if the policy collects every session. An org admin sets this on **Team settings → Data collection**.

## How it works

Terma configures Codex at the user level. Nothing is written into your repositories.

### Telemetry: Codex's OpenTelemetry export

`terma setup` points the `[otel]` exporter in `~/.codex/config.toml` at a relay terma runs on your machine, on `127.0.0.1`. The relay forwards only sessions that a hook claimed in a repository your team collects, with your team's key, and drops everything else on your machine. Your team's key never appears in Codex's configuration.

This channel carries model calls with their token counts and cost, tool calls, and — when your team's policy collects them — prompts, responses, and tool content. Setup also routes Codex's `notify` setting through terma to capture turns, and keeps any notifier you already had.

Terma also reads Codex's local session log for activity Codex's telemetry does not report, such as hosted actions and compactions.

### Attribution: machine-wide hooks

`terma setup` adds these entries to `~/.codex/hooks.json`:

| Hook | What Terma records |
|---|---|
| `SessionStart` | The session begins |
| `UserPromptSubmit` | A turn begins |
| `PermissionRequest` | Codex asked for approval, labeled **requested** — Codex does not tell hooks whether you approved or denied |
| `PostToolUse` | Tool calls and the files each edit touches |
| `Stop`, `SessionEnd` | A turn or the session ended, with token usage and plan usage windows |
| `SubagentStart`, `SubagentStop` | Subagents the session spawns |

Each command is guarded, so on a machine without terma it does nothing. Hooks never make a network request: they append to a local queue that terma delivers in the background. Set `TERMA_HOOKS=0` to turn them off for one shell or process.

When your team's policy stamps commits, the first session in a collected repository also installs commit hooks in that repository's `.git/hooks`. See [Commit attribution](/concepts/attribution).

## What's captured

| Signal | Source |
|---|---|
| Sessions, turns, and subagents | Hooks and OpenTelemetry |
| Model calls, tokens, and cost | OpenTelemetry |
| Tool calls | OpenTelemetry and hooks |
| Prompts and responses | When your team's policy collects prompts |
| Tool input and output | When your team's policy collects tool content |
| Files edited, for commit attribution | Hooks |
| Plan usage windows and credits | Hooks |

<Note>
  Some of this capture reads Codex's private local session format, which can change between Codex releases, and Codex exempts some hosted and specialized tools from hooks. New Codex item types may require a terma update; run `terma update`.
</Note>

## Controlling what is sent

Your team's collection policy decides what leaves your machine. An org admin sets it on **Team settings → Data collection**. The local relay removes what the policy does not collect before anything leaves. See [Privacy and data](/concepts/privacy).

## Verify

```bash
terma doctor
```

`doctor` checks your sign-in, whether your team collects the current repository, the hooks and whether Codex trusts them, Codex's export, and delivery to Terma. It also warns when a Codex process started before setup is still exporting where it did; restart it. Every failure names its fix, usually `terma setup`.

<Tip>
  An organization that deploys Codex configuration centrally can write terma's hooks as a `requirements.toml`, which Codex runs with no trust step: `terma setup --managed-config <dir>`.
</Tip>
