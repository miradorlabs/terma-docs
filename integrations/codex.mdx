Terma supports both ways of running OpenAI's Codex, and treats them as separate choices:

- **Codex CLI** — the `codex` shell command. Usage and cost arrive through Codex's own OpenTelemetry export, routed to the repository's project each time you launch `codex`.
- **Codex Desktop** — the desktop app, which does not launch through your shell. It reports through repository hooks and Terma's local spool.

Both use the repository's `.codex/hooks.json` to attribute commits.

## Codex CLI

### Set up

```bash
cd your-repo
terma install --harness codex
```

Reload your shell as `install` tells you (for zsh, `source ~/.zshrc`), commit the files it lists, then trust the hooks in Codex (see [Trust the hooks](#trust-the-hooks)).

### How it works

Codex ignores telemetry settings in a repository's own configuration, so a direct Codex export is always machine-wide. `terma install` works around this: it puts a small `codex` shim first on your `PATH`, and each time you run `codex` in the repository, the shim passes the repository's telemetry settings as launch-time `-c` overrides. Your own Codex home directory, login, history, trust settings, and notifier are left as they are.

This channel carries model calls with their token counts and cost, tool calls, and — unless you turn them off — prompts and responses.

<Warning>
  The launch-time overrides include the project's telemetry key, which local process inspection can see. Do not log the arguments that agent launchers generate.
</Warning>

Codex sessions carry your identity as `enduser.id`, taken from your `git user.email` by default. Change it with `terma install --identity <value>`, or pass `--identity none` to omit it.

## Codex Desktop

### Set up

1. Choose **Codex Desktop** in `terma setup`, or run `terma install --harness codex-desktop` in a repository. Choose **Codex CLI** too if you also use the shell command.
2. Run `terma install` in each repository you want to report. It binds the project, stores a project key and content policy on your machine, and writes the Codex hooks for you to commit.
3. Approve the hooks in Codex Desktop:
   1. Open the repository in Codex Desktop and trust the project if prompted.
   2. Open **Settings → Hooks** and select **Review** for the entries from this repository's `.codex/hooks.json`. If hooks are disabled, enable them there.
   3. Inspect the `terma hook …` commands and approve each Terma entry. Codex skips any entry you leave untrusted.
4. Run `terma desktop status` in the repository. **Codex hooks: ready** confirms the current definitions are trusted.
5. Start a new **Local** task in that repository, send a test message, and run `terma doctor` to verify delivery.

Terma installs no background receiver, launch agent, or global Codex exporter for Desktop.

### What Desktop capture includes

- Sessions and turns, with prompt text only if the repository allows prompts
- Local tool calls and their results, with arguments and output only if the repository allows tool content
- Per-response token usage, turn duration, and time to first token, read from Codex's local session log
- Approval requests, labeled **requested** — Codex does not tell hooks whether you approved or denied
- Files edited, for commit attribution

<Note>
  Desktop capture reads Codex's private local session format, which can change between Codex releases, and Codex exempts some hosted and specialized tools from hooks. Terma cannot guarantee every Desktop tool call is captured, and new Codex item types may require a Terma update.
</Note>

## Trust the hooks

Codex runs repository hooks only after you trust them, and asks again whenever a hook definition changes — for example after `terma update --refresh`. `terma install` never approves hooks on your behalf.

- **Codex CLI:** run `/hooks` inside Codex and approve the Terma entries.
- **Codex Desktop:** open **Settings → Hooks → Review** and approve the Terma entries.

`terma doctor` reports untrusted hooks under **agent hooks run**.

## Repository hooks

`install` adds these entries to `.codex/hooks.json`:

| Hook | What Terma records |
|---|---|
| `SessionStart` | The session begins |
| `UserPromptSubmit` | A turn begins, with prompt text if allowed |
| `PreToolUse`, `PostToolUse` | Tool calls, their observed duration, and the files each edit touches |
| `PermissionRequest` | Codex asked for approval |
| `Stop`, `SessionEnd` | A turn or the session ended, with token usage and plan usage windows |
| `SubagentStart`, `SubagentStop` | Subagents the session spawns |

Each command is guarded, so on a machine without Terma it does nothing.

## What's captured

| Signal | Codex CLI | Codex Desktop |
|---|---|---|
| Sessions, turns, and subagents | Yes | Yes |
| Model calls, tokens, and cost | Yes (OpenTelemetry) | Tokens per response (session log) |
| Tool calls | Yes | Local tools; some hosted tools are exempt |
| Prompts and responses | Unless `--prompts off` | If the repository allows prompts |
| Files edited, for commit attribution | Yes | Yes |
| Plan usage windows and credits | Yes | Yes |

<Note>
  `--exclude-tool-content` stops Codex from exporting tool output, but Codex cannot suppress native tool arguments.
</Note>

## Verify

```bash
terma status            # the Agent line should show Codex exporting to this project
terma desktop status    # Codex Desktop: are this repository's hooks trusted?
terma doctor            # proves hooks stamp a commit and events reach Terma
```

`terma desktop status` also reports a separate, user-level Codex exporter if one is active, since that can send Desktop activity from other repositories. Use `terma disconnect codex` to remove a Terma-owned one.

<Tip>
  For Codex-managed local worktrees, a Git-ignored `.terma/settings.json` must be copied into the worktree. Add it to `.worktreeinclude` if needed.
</Tip>
